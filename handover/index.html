Project handover

Bino Foundry

This package explains how to configure, deploy, and take ownership of the project. Use the tabs below. It is written for a technical successor who did not build the original stack.

1. Code merged to main dev branch kept 3–7: use these tabs

What this handover covers

Bino Foundry is a monorepo for a jewellery customiser: a crystal bracelet builder, a sunglasses customiser, and an admin catalogue. The browser talks to an Express API. Supabase holds Postgres and file storage only. Email is sent through SMTP settings stored in the application (currently the outgoing developer mailbox until you replace it).

Already done. Source code is in your GitHub repository. The current dev work is merged into main. Keep dev as a working branch. CI on GitHub Actions builds and tests on every push to main.

3. Configuration

Think of configuration as three places, not one .env dump. Backend secrets stay on the server. Frontend env is baked into the browser bundle at build time. Email SMTP is not in env files at all — it is saved in the admin website.

Backend env Frontend env Admin website Third-party dashboard

Which env files are real? (root vs backend vs frontend)

Yes — the API uses the repo-root .env. The file backend/.env.example is only a short reminder. It is not where production secrets live. Fill .env (or .env.production) next to the root package.json. That is what Express loads.

Two different .env.production files — do not mix them up.
  • .env.production (repo root) — Express API secrets (SUPABASE_*, JWT_SECRET, ADMIN_API_KEY, CORS_ORIGINS, …). Template: deploy/env/.env.production.example.
  • frontend/.env.production — SPA only (VITE_API_BASE_URL, optional VITE_ADMIN_API_KEY, VITE_API_PREFIX). Template: frontend/.env.production.example. On a single-VPS nginx setup, leave VITE_API_BASE_URL empty so the browser calls same-origin /api.

Backend search order (later files win; shell exports always win): root .env → .env.local → .env.{APP_ENV} → .env.{APP_ENV}.local, also checked under deploy/env/ and optionally backend/. Code: backend/src/config/load-env.ts.

Frontend: which file for local / staging / production?

Vite picks files by mode (from the npm script). It loads both repo root and frontend/, then merges. Values in frontend/ win over the same key in the root. If VITE_ADMIN_API_KEY is empty, Vite copies root ADMIN_API_KEY automatically.

Do not confuse templates with live files. Anything ending in .example is documentation only. The running API will not read backend/.env.example. If only frontend env files are filled and root .env is empty, the backend has no Supabase keys and the API will fail in staging/production.

Merge logic: frontend/vite-resolve-env.ts + frontend/src/config/vite-env-merge.ts.

How root + frontend work together

The browser never talks to Supabase with the service role. The SPA calls /api/… on your backend. The backend uses root-env SUPABASE_URL + SUPABASE_SERVICE_ROLE_KEY to read/write Postgres and Storage.

  • Local: put secrets in root .env; put VITE_API_BASE_URL=http://localhost:5050 in frontend/.env.development.local.
  • Single VPS (nginx): secrets in root .env.production; leave VITE_API_BASE_URL empty in frontend/.env.production so the SPA uses same-origin /api.
  • ADMIN_API_KEY (root / backend) and VITE_ADMIN_API_KEY (frontend) must be the same string. The admin UI sends it as x-api-key on create/update/delete. If you omit the Vite variable, the build copies root ADMIN_API_KEY automatically.

Where to get third-party credentials

Supabase Dashboard

Database (Postgres) and file storage for frames, beads, and uploads. App login is not Supabase Auth — users live in the users table and the API issues JWTs.

  1. Open supabase.com/dashboard and select the transferred project.
  2. Go to Project Settings → API.
  3. Copy Project URL → paste as SUPABASE_URL in root .env.
  4. Copy service_role (secret) → SUPABASE_SERVICE_ROLE_KEY in the same file. Never expose this in the browser.
  5. Anon / publishable key is optional leftover (SUPABASE_ANON_KEY). You can leave it empty.
  6. Confirm Storage buckets still exist (catalogue images). If the site shows broken images, buckets or policies did not transfer.

Email SMTP Admin UI

Not an env variable. Credentials are stored in the database, encrypted with SETTINGS_ENCRYPTION_KEY.

  1. Create a mailbox at Google Workspace, Amazon SES, Postmark, Resend SMTP, or similar.
  2. From that provider, copy host, port (often 587), username, password, and from-address.
  3. In the website UI: open /admin → left nav General settings → scroll to SMTP configuration (URL /admin/general-settings).
  4. Fill SMTP, enable it, save, then use Test SMTP connection.
  5. In code/server env (repo root .env.production), set PUBLIC_APP_URL to the public site URL so reset/verify links are correct.

Secrets you generate yourself

JWT_SECRET, SETTINGS_ENCRYPTION_KEY, and ADMIN_API_KEY are not from a vendor. Generate them once and store in a password manager.

node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
# SETTINGS_ENCRYPTION_KEY: use that base64 output
# JWT_SECRET and ADMIN_API_KEY: another long random string each (min 32 chars for JWT)

If you rotate SETTINGS_ENCRYPTION_KEY, open admin and re-save SMTP (old ciphertext cannot be decrypted).

Backend variables (in root .env, not backend/.env.example)

Copy .env.example → .env (local) or deploy/env/.env.production.example → root .env.production (VPS). The Express process reads these via backend/src/config/load-env.ts. Check with npm run env:check.

Variable Get it from Put it in What it is used for
APP_ENV You set it Backend .env development / staging / production. Staging and production require Supabase, CORS, JWT, admin key, and encryption key.
NODE_ENV You set it Backend .env Usually production on the server. Node runtime mode, not the same as APP_ENV.
PORT You set it Backend .env Port the API listens on. Default 5050 (macOS often blocks 5000 for AirPlay). Nginx proxies /api here.
TRUST_PROXY You set it Backend .env Set 1 behind nginx/Caddy so HTTPS and client IP are trusted. Local: 0.
SUPABASE_URL Supabase → Settings → API → Project URL Backend .env Base URL of the Postgres + Storage project, e.g. https://xxxx.supabase.co. Required for catalogue, uploads, and saved designs.
SUPABASE_SERVICE_ROLE_KEY Supabase → Settings → API → service_role Backend .env never frontend Server key that bypasses row-level security. The API uses it for all DB and storage work. If this is wrong, admin saves and images fail.
SUPABASE_ANON_KEY Supabase anon key (optional) Backend .env Legacy. Not used for login. Safe to leave blank.
PUBLIC_APP_URL Your public website URL Backend .env Origin used in password-reset and email-verification links. Example: https://binofoundry.builtbyroni.com. Defaults to the first CORS origin if empty.
CORS_ORIGINS You set it (your SPA URL) Backend .env Comma-separated browser origins allowed to call the API. No trailing slash. Must match the real site URL or the browser blocks requests. Local dev still allows localhost even if this lists only production.
JWT_SECRET You generate it (32+ chars) Backend .env Signs login tokens. Changing it logs everyone out. Keep it secret and stable in production.
SETTINGS_ENCRYPTION_KEY You generate it (base64 32 bytes) Backend .env Encrypts SMTP passwords in the database. Required or admin cannot store mail credentials.
JWT_ACCESS_TTL_SECONDS You set it Backend .env Access token lifetime. Default 900 (15 minutes).
JWT_REFRESH_TTL_DAYS You set it Backend .env Refresh token lifetime. Default 30 days.
ADMIN_API_KEY You generate it Backend .env + same value on frontend Required for catalogue create/update/delete. Staff still log in with email/password; this key is an extra guard on write APIs. Must match VITE_ADMIN_API_KEY.

Frontend variables (VITE_* only)

Use the mode matrix above. Prefer frontend/.env.development.local for laptop work and frontend/.env.production on the VPS. Templates: frontend/.env.example, frontend/.env.staging.example, frontend/.env.production.example. After changing these, rebuild the SPA.

4. Deployment

This tab is a first-time deploy onto a new Ubuntu VPS (not a domain migration). One server runs everything: nginx serves the SPA from /var/www/bino-foundry, proxies /api to Node on 127.0.0.1:5050, and the Git repo lives under /opt/bino-foundry. Supabase stays in the cloud.

Replace every YOUR_DOMAIN below with your real hostname (e.g. shop.example.com). Repo nginx templates may still contain an old example hostname — always edit server_name and certificate paths to match your domain. There is no application cron; CI runs on push to main only.

What you need before starting

  • A new Ubuntu 22.04 or 24.04 VPS (2 GB RAM recommended; 1 GB needs swap for builds).
  • SSH access (root or sudo).
  • DNS A record: YOUR_DOMAIN → this VPS public IPv4 (propagate before certbot).
  • Supabase Project URL + service_role key (see Configuration).
  • Git clone access to this repository.

Server layout

Path on VPS Role

/var/www/bino-foundry Published SPA only (synced from frontend/dist)
127.0.0.1:5050 API process (PM2 or systemd), proxied at /api
deploy/nginx/ (in repo) nginx site templates — copy to /etc/nginx/sites-available/

Step 1 — Packages, firewall, Node, PM2

ssh root@YOUR_VPS_IP

apt update && apt upgrade -y
apt install -y git nginx certbot python3-certbot-nginx ufw

ufw allow OpenSSH
ufw allow 'Nginx Full'
ufw --force enable

curl -fsSL https://deb.nodesource.com/setup_20.x | bash -
apt install -y nodejs
node -v   # v20.x
npm install -g pm2

Step 2 — Clone repo and web root

mkdir -p /opt
cd /opt
git clone YOUR_REPO_URL bino-foundry
cd bino-foundry
git checkout main

sudo mkdir -p /var/www/bino-foundry

Step 3 — Backend env (repo root)

File on server: /opt/bino-foundry/.env.production (template in repo: deploy/env/.env.production.example). 

cd /opt/bino-foundry
cp deploy/env/.env.production.example .env.production
nano .env.production
APP_ENV=production
NODE_ENV=production
PORT=5050
TRUST_PROXY=1

SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_SERVICE_ROLE_KEY=your_service_role_key_here

PUBLIC_APP_URL=https://YOUR_DOMAIN
CORS_ORIGINS=https://YOUR_DOMAIN

JWT_SECRET=generate_a_long_random_string_min_32_chars
SETTINGS_ENCRYPTION_KEY=paste_base64_32_byte_key_here
ADMIN_API_KEY=choose_a_long_random_secret

Validate: APP_ENV=production npm run env:check.

Step 4 — Frontend env (folder frontend/)

File: /opt/bino-foundry/frontend/.env.production. Leave VITE_API_BASE_URL empty for same-origin /api via nginx. 

cat > frontend/.env.production <<'EOF'
VITE_API_BASE_URL=
VITE_API_PREFIX=/api
VITE_ADMIN_API_KEY=same_value_as_ADMIN_API_KEY
EOF

Step 5 — Build

Small VPS builds often fail with exit 137 (out of memory). Add swap once, then build. 

# One-time 2G swap if the VPS has ≤2 GB RAM
sudo fallocate -l 2G /swapfile || sudo dd if=/dev/zero of=/swapfile bs=1M count=2048
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

cd /opt/bino-foundry
npm ci
npm run build:all
# outputs: backend/dist/  and  frontend/dist/
npm run deploy:build — optional helper. Same outcome as npm ci + npm run build:all, plus extras when available on the VPS:
  • Creates a temporary 2G swapfile if none exists (needs root).
  • If PM2 already runs bino-foundry-api, stops it during the Vite build to free RAM, then restarts it afterward.
Prefer this on a small VPS after the first deploy. For a brand-new VPS (API not running yet), npm run build:all is enough once swap exists.

Step 6 — Publish SPA to nginx root

cd /opt/bino-foundry
sudo npm run deploy:web
# syncs frontend/dist → /var/www/bino-foundry

Step 7 — Start the API (PM2 recommended)

Config file in repo: deploy/pm2/ecosystem.config.cjs.

cd /opt/bino-foundry
pm2 start deploy/pm2/ecosystem.config.cjs --env production
pm2 save
pm2 startup
pm2 status
pm2 logs bino-foundry-api
Alternative: systemd (deploy/systemd/bino-foundry-api.service). Use this if you prefer OS-level process management instead of PM2. The unit runs node backend/dist/server.js from /opt/bino-foundry, loads .env.production, and restarts on failure. 
sudo cp deploy/systemd/bino-foundry-api.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now bino-foundry-api
sudo systemctl status bino-foundry-api
Do not run PM2 and systemd for the same API at once (port conflict). Pick one. This guide’s later steps assume PM2 unless you switched.

Step 8 — nginx (HTTP first)

Vendor-neutral starter: deploy/nginx/bino-foundry.conf. Or copy a full example from deploy/nginx/ and replace every hostname with YOUR_DOMAIN. The site must include: root /var/www/bino-foundry, location /api/ → 127.0.0.1:5050, and try_files $uri $uri/ /index.html; for SPA routes (/bracelet, /admin, …). 

cd /opt/bino-foundry
sudo cp deploy/nginx/bino-foundry.conf \
  /etc/nginx/sites-available/YOUR_DOMAIN.conf

# Edit server_name to YOUR_DOMAIN
sudo nano /etc/nginx/sites-available/YOUR_DOMAIN.conf

sudo ln -sf /etc/nginx/sites-available/YOUR_DOMAIN.conf \
  /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx

Step 9 — HTTPS (Let’s Encrypt)

sudo certbot --nginx -d YOUR_DOMAIN
sudo certbot renew --dry-run
After certbot — re-apply the repo HTTPS template. Certbot often rewrites the nginx site and can drop SPA try_files on port 443. If that happens, refreshing /bracelet returns nginx 404 instead of the React app. Prefer installing the repo HTTPS example (edit hostname + certificate paths to YOUR_DOMAIN), then reload nginx: 
sudo cp deploy/nginx/binofoundry.temukreatif.id.https.conf \
  /etc/nginx/sites-available/YOUR_DOMAIN.conf
# replace every old hostname with YOUR_DOMAIN
# ssl paths become /etc/letsencrypt/live/YOUR_DOMAIN/...
sudo nano /etc/nginx/sites-available/YOUR_DOMAIN.conf
sudo nginx -t && sudo systemctl reload nginx
Keep: HTTP→HTTPS redirect, /api/ proxy, and try_files $uri $uri/ /index.html; on 443.

Step 10 — Smoke test

  • https://YOUR_DOMAIN/ — site loads
  • https://YOUR_DOMAIN/api/status — public liveness JSON
  • /api/health — detailed checks; requires x-api-key in production
  • /api/docs — Swagger; disabled in production (local only unless ENABLE_API_DOCS=1)
  • https://YOUR_DOMAIN/admin — admin login
  • Refresh /bracelet — must stay on the app (SPA try_files)
  • Admin → General settings — set SMTP and send a test

Update after a git pull

cd /opt/bino-foundry
git pull origin main
npm run deploy:build   # or: npm ci && npm run build:all
sudo npm run deploy:web
pm2 restart bino-foundry-api
# if using systemd instead: sudo systemctl restart bino-foundry-api

If you change any VITE_* value, rebuild is required — those values are baked into frontend/dist.

5. Access

After handover, you should be able to run the product without the original developer. Grant yourself owner access first, verify it, then revoke the developer.

GitHub

  1. Confirm you own or are admin on the repository (example remote: BinoFoundry/bino-foundry).
  2. Keep branches main (release) and dev (ongoing work).
  3. Add your deploy keys or GitHub Actions secrets if the VPS pulls privately.
  4. After you can clone, push, and see green CI, remove the developer as collaborator.

Supabase

  1. You should be Owner of the transferred project.
  2. Copy the new Project URL and service role key into production .env.
  3. Confirm Storage buckets and catalogue images still load in the builders.
  4. Remove the developer from the org once the live site uses your project keys.

Application admin

Staff login is application JWT against the users table, not Supabase Auth. Catalogue writes also need ADMIN_API_KEY / VITE_ADMIN_API_KEY.

  1. Create or promote an admin user you control.
  2. Sign in at /admin and save a harmless catalogue change.
  3. Rotate ADMIN_API_KEY if it was shared during development; rebuild the SPA if the Vite key is baked in.
  4. Disable or delete the developer admin account.

VPS / domain / email

  • SSH on the production VPS, plus DNS A record for your live hostname.
  • Let’s Encrypt renewal (certbot timer is enough; no extra app cron).
  • Replace SMTP with your mailbox (see Configuration).
Revoke last. Do not remove developer access until GitHub, Supabase, admin login, and a production (or 30-day) site all work with your credentials.

7. Development notes

Milestone 1 foundations are signed off. Milestone 2 delivered the contracted builders and admin catalogue, plus a large amount of render/calibration work on dev that is now on main. This is not a finished e-commerce shop.

Completed

  • Monorepo: Vite/React SPA, Express API, shared types, SQL migrations, deploy configs.
  • Supabase as Postgres + Storage only; business logic in Express.
  • Sunglasses customiser: frames, lenses, tints, 2D layered preview, clip pipeline.
  • Crystal bracelet builder: libraries, sizing, occupancy, mobile layout, zoom.
  • Admin dashboard: frames, tints, beads/charms, pricing-related settings, media.
  • Application auth (JWT), SMTP settings, site settings, and the order request flow (customer submit → admin Orders UI, snapshots). Payment gateway (Stripe etc.) is not included — see unfinished below.
  • Strand / bead calibration: per-field Customize (render size, occupancy, vertical offset, orientation, layout mode, advanced). Parent calibration is inherited unless a column is customized. Render size may be below 1.0.

Unfinished or out of original polish scope

  • Pre-built / ready-made bracelets (additional request — not built): customers should be able to pick a finished bracelet from a catalogue without using the strand builder. Today the customer path is still “build your own” in the bracelet builder. Needs: admin way to publish curated designs, a customer browse/select UI, and checkout wiring for those SKUs. Not started.
  • Payment / paid checkout: order requests already work in-app (no card charge). For remaining commerce gaps, open docs/MILESTONE2_COMMERCE_CHECKLIST.md.
  • 3D / WebGL: explicitly out of scope unless the contract is amended.
  • Email: still on the previous developer SMTP until you replace it in Admin → General settings.
  • Hostnames in repo templates: some files under deploy/nginx/ still use an old example hostname; always replace with YOUR_DOMAIN on a new VPS.
  • Further visual polish, marketing pages, and legal copy (terms/privacy) may still need client content.

What to verify after handover

  1. Bracelet: change wrist size, add beads, confirm occupancy and preview.
  2. Sunglasses: change frame, tint, and lens; confirm clip and price.
  3. Admin: edit a bead render size with Customize on one column only; confirm inherit vs override.
  4. Auth: register, verify email (after SMTP is yours), reset password.
  5. CI: push a trivial commit to dev or a PR into main and wait for green.
